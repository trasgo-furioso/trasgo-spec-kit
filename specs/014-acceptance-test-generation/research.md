# Research: Acceptance Test Generation

**Date**: 2026-08-21 | **Feature**: 014-acceptance-test-generation

## Decision: AI-Only Command (No Bash Script)

**Decision**: The command file contains only YAML frontmatter (`description`, no `scripts` key) and markdown body with AI agent instructions. No deterministic bash script.

**Rationale**: All command logic (spec parsing, frontend analysis, code generation) is inherently AI-driven — there is no deterministic transformation that a bash script could perform. The `speckit.trasgospec.hello` command establishes this precedent.

**Alternatives considered**:
- Bash script for spec parsing + AI for code generation: Rejected because Markdown parsing of nested GWT scenarios with bold formatting requires context-aware parsing better suited to an LLM than regex.
- Standalone TypeScript CLI tool: Rejected because it would violate Principle I (Composition Over Creation) by creating a parallel system outside the bundle command model.

## Decision: GWT Structure via `test.step()`

**Decision**: Use Playwright's `test.step()` API to wrap Given/When/Then sections instead of plain comments.

**Rationale**: `test.step()` sections appear in Playwright's trace viewer and HTML reports, providing runtime visibility into which GWT phase failed. Plain comments are invisible at runtime. Research confirmed this as the modern Playwright-native approach (Playwright docs, multiple best-practice guides).

**Alternatives considered**:
- Plain inline comments (`// Given / Arrange`): Simpler but invisible in traces/reports.
- Cucumber/Gherkin runner (`playwright-bdd`): Rejected because it adds a dependency and a separate feature file layer that duplicates the spec.md scenarios.

## Decision: Page Object Model with Composition

**Decision**: Page objects are standalone TypeScript classes injected via `test.extend<>()` fixtures. No inheritance chains.

**Rationale**: Research confirmed composition is the modern consensus. Inheritance chains (`BasePage -> AuthenticatedPage -> AdminPage`) create hidden coupling, fragile APIs, and break when navigation or layout changes. Composition allows small, focused page/component objects that can be mixed freely via fixtures.

**Alternatives considered**:
- Inheritance-based POM (`extends BasePage`): Rejected due to coupling and fragility.
- No POM (inline selectors): Rejected because it makes tests unmaintainable and violates the selector reuse contract.

## Decision: Accessibility-First Selector Hierarchy

**Decision**: `getByRole` > `getByLabel` > `getByText` > `getByTestId` > never CSS.

**Rationale**: This matches Playwright's official recommendation and Testing Library's query priority. Role-based selectors test the same interface that assistive technology uses, catching both test failures and accessibility regressions simultaneously.

**Alternatives considered**:
- CSS-first with test IDs: Rejected because CSS selectors are brittle and don't verify accessibility.
- Test IDs only: Rejected because test IDs don't verify that the component is semantically correct.

## Decision: Traceability Header Marker

**Decision**: Each generated file begins with a structured comment block containing a fixed sentinel string, spec path, user story reference, and generation timestamp. The exact format is:

```typescript
/**
 * @generated by speckit.trasgospec.acceptance-tests
 * @spec specs/014-feature/spec.md
 * @story US1 - Core Test Generation
 * @generated-at 2026-08-21T14:30:00Z
 *
 * DO NOT DELETE this header block. It identifies this file as agent-generated
 * and enables incremental updates when the spec changes.
 */
```

**Rationale**: The `@generated by speckit.trasgospec.acceptance-tests` sentinel on line 2 is grep-friendly, unlikely to appear in manual tests, and machine-parseable. The metadata fields enable incremental updates (FR-022) and bidirectional navigation (FR-015/SC-002).

**Alternatives considered**:
- JSON block comment: More machine-parseable but less human-readable.
- Playwright annotation metadata: Doesn't persist in the file — only available at runtime.
- File naming convention only: Not reliable enough — collisions with manual tests possible.

## Decision: Story-Level Acceptance Gates

**Decision**: Implementation phases map to user stories. Each story's generated E2E tests serve as the acceptance gate. A phase is complete when all its acceptance tests pass.

**Rationale**: This aligns with the spec's user story priority model (P1→P2→P3) and the speckit-implement workflow where tasks are grouped by story. Progressive green — tests start red, implementation turns them green one story at a time.

**Alternatives considered**:
- All-or-nothing gate: Rejected because it blocks progress when lower-priority stories are incomplete.
- Per-test progressive: Too granular — loses the story-level coherence that maps to implementation phases.

## Decision: Testing Surface Contract Format

**Decision**: Contracts use a Markdown template with standardized tables (Parts, States, Supported Actions) plus Provider/Consumer Obligations sections. Shipped as a preset template.

**Rationale**: Fits the existing speckit-plan contract pattern (Markdown files in `contracts/`). The Parts table declares the testing surface as a versioned provider/consumer API. Research confirmed this as an emerging best practice for contract-driven testing.

**Alternatives considered**:
- JSON/YAML contract file: More machine-parseable but breaks the Markdown-first convention of all spec artifacts.
- TypeScript interface file: Would require a build step and breaks the language-agnostic spec layer.
- No explicit contract (infer from code): Rejected because it couples test generation to implementation order and prevents independent development.
